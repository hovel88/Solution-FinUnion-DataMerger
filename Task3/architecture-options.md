# architecture-options.md — сравнение архитектурных вариантов: FinUnion + RetailBank

> Назначение документа: сравнить три архитектурных подхода к организации данных для объединённой компании: DWH на PostgreSQL (классический), Data Lakehouse (современный), Data Mesh (организационный). Выбрать целевой подход (12 месяцев) и обосновать.

## Подход 1: DWH на PostgreSQL

### 1.1. Плюсы

- Гарантия целостности данных (ACID)
- Стандартный язык SQL, знаком команде
- PostgreSQL — проверенная, зрелая, надёжная СУБД
- Open-source, не требует лицензий
- Легко начать с классического DWH, не требует новой инфраструктуры, если в системе уже есть PostgreSQL
- Хорошо подходит для регулятора (регламентированная отчётность)

### 1.2. Минусы

- PostgreSQL не масштабируется на петабайты
- Не подходит для плохоструктурированных данных (логи, события, JSON)
- Нет streaming, только batch (ETL)
- Не для machine learning

### 1.3. Когда подходит

- Небольшие объёмы данных (терабайты)
- Структурированные данные
- Регламентированная отчётность
- Ограниченный бюджет
- Зрелая команда, которая знает SQL

### 1.4. Применимость к кейсу FinUnion + RetailBank

| Аспект | Оценка | Объяснение |
| -- | -- | -- |
| Промежуточное состояние (3 месяца) | **Подходит** | быстрый старт, DWH  легко организовать на PostgreSQL |
| Целевое состояние (12 месяцев) | **Частично** | не хватает для истории, событий, ML |
| Объём | **Плохо** | до терабайт, может не хватить |
| Регламентированная отчётность | **Подходит** | как раз самое оно |
| Антифрод (ML) | **Не подходит** | не для ML |

## Подход 2: Data Lakehouse

### 2.1. Плюсы

- Хорошо масштабируется до петабайт (S3)
- S3 обходится дешевле, чем DWH
- Позволяет работать с плохоструктурированными данными (JSON, логи, события)
- Есть streaming (из Kafka в Lakehouse)
- Есть возмосжность использовать сырые данные для ML
- Высокая гибкость из-за Schema-on-read
- обеспечивает воспроизводимость благодаря снимкам в Iceberg

### 2.2. Минусы

- Высокая сложность, требуется экспертиза (Iceberg, Trino, S3)
- Нет транзакционности, не для ACID нагрузки
- Нет привычного прямого SQL-доступа, можэно организовать через Trino, но это медленнее и с ограничениями
- Высокая стоимость решения, нужно посчитать затраты на S3 + Trino + Iceberg

### 2.3. Когда подходит

- Большие объёмы (петабайты)
- Плохоструктурируемые данные данные (JSON, логи, события)
- Позволяет работать с ML (антифрод)
- Есть streaming (real-time)
- Высокая гибкость (schema-on-read)

### 2.4. Применимость к кейсу FinUnion + RetailBank

| Аспект | Оценка | Объяснение |
| -- | -- | -- |
| Промежуточное состояние (3 месяца) | **Не подходит** | слишком сложно для быстрого старта |
| Целевое состояние (12 месяцев) | **Подходит** | история, события, ML — всё можно реализовать |
| Объём | **Подходит** | масштабируется до петабайт |
| Регламентированная отчётность | **Частично** | хуже чем DWH |
| Антифрод (ML) | **Подходит** | |

## Подход 3: Data Mesh (организационный подход)

### 3.1. Плюсы

- Хорошая масштабируемость (организационная), т.к. домены сами владеют данными
- Быстрый выпуск данных, т.к. домены сами публикуют Data Products
- Высокое качество данных, т.к. в домене есть владелец, который отвечает за качество
- Домены сами выбирают инструмент для себя, это увеличивает гибкость

### 3.2. Минусы

- Высокая организационная сложность, нужна зрелая культура команде
- Требует платформы (self-serve platform: Airflow, DataHub)
- Избыточен для небольших компаний
- Очень долгий старт

### 3.3. Когда подходит

- Крупные компании (где много доменов)
- Зрелая культура данных
- Много Data Products

### 3.4. Применимость к кейсу FinUnion + RetailBank

| -- | -- | -- |
| Промежуточное состояние (3 месяца) | **Не подходит** | слишком рано |
| Целевое состояние (12 месяцев) | **Частично** | можно начать формировать Data Products |
| Регламентированная отчётность | **Подходит** | |

## Выбор целевого подхода

Ни один из подходов не покрывает все требования целевого (12 месяцев) состояния системы. Но каждый из них закрывает свою часть требований. Выбираем **гибридный** подход, чтобы использовать лучшие стороны каждого варианта:

- Регламентированная отчётность покрывается DWH (PostgreSQL / Greenplum)
- История транзакций покрывается Lakehouse (CDC из Core)
- События (антифрод) покрывается Lakehouse (streaming из Kafka)
- ML покрывается Lakehouse (сырые данные)
- BI покрывается DWH и частично Lakehouse (Trino)
- Трассируемость и полный Lineage покрывается DataHub
- Организационная масштабируемость покрывается Data Mesh (Data Products)

| Слой | Компонент | Роль |
|------|-----------|------|
| **OLTP** | FU CRM / Core / Cards / Loans | Транзакционные системы |
| **MDM** | MDM Customer Hub / Product Catalog / Reference Data Management | Золотые записи |
| **Integration Layer** | API Gateway, Kafka, Debezium | Sync/async/CDC |
| **Оркестрация** | Airflow | Batch, ETL-пайплайны |
| **BI** | BI | Дашборды |
| **OLAP (DWH)** | DWH (PostgreSQL / Greenplum) | Регламентированная отчётность, BI-витрины |
| **OLAP (Lakehouse)** | Lakehouse (S3 + Iceberg + Trino) | История, события, логи изменений, ML |
| **Каталог** | DataHub | Метаданные, lineage, трассируемость данных |
| **Data Products** | Customer 360, и т.д. | Доменные data products |

Применение гибридного подхода можно разделить на этапы:

- промеждуточное состояние (3 месяца): DWH на PostgreSQL + Integration Layer + Kafka
- промежуточное состояние (6-9 месяцев): добавляем Lakehouse (S3 + Iceberg + Trino) + MDM + CDC (Debezium)
- целевое состояние (12 месяцев): добавляем Data Products (Data Mesh) + DataHub (полный lineage)
