# dwh-lakehouse.md — сравнение DWH на PostgreSQL и Data Lakehouse: FinUnion + RetailBank

> Назначение документа: детально сравнить классический DWH (на PostgreSQL) и Data Lakehouse для кейса FinUnion + RetailBank. Определяется что попадает в DWH, что в Lakehouse и почему, какую роль играют инструменты.

## Классический DWH (на PostgreSQL)

DWH — классическое реляционное хранилище для аналитики. Данные загружаются через ETL (Airflow), хранятся в структурированном виде (схема "звезда" или "снежинка"), используются для регламентированной отчётности и BI-витрин.

### Плюсы DWH для FinUnion + RetailBank

- Гарантия целостности финансовых данных (ACID)
- Стандартный, знакомый команде язык SQL
- PostgreSQL это проверенная зрелая стабильная СУБД (можно реализовать на Greenplum, который тоже PostgreSQL-based)
- Нет лицензий (open-source), дли бизнеса обходится дешевле
- Зачастую в инфраструктуре уже есть операционная PostgreSQL, поэтому не требует нового стека и оказывается проще в развертывании
- Хорошо подходит для регулятора, для регламентированной отчётности

### Минусы DWH для FinUnion + RetailBank

- Не для плохоструктурированных (JSON, логи, события) данных
- На большие данные (петабайты) сложно масштабируется или вообще не масштабируется
- Нет streaming, только batch (ETL)
- Не подходит для работы с ML (например, для антифрод)

### Когда DWH подходит

- Когда небольшие объёмы (терабайты)
- Когда данные структурированные
- Когда требуется регламентированная отчётность
- Когда ограниченный бюджет, а PostgreSQL зачастую и так уже есть в проекте
- Когда зрелая команда, знающая SQL

## Data Lakehouse

Data Lakehouse это гибрид Data Lake (S3) и DWH. Когда данные хранятся в открытых форматах (Parquet, ORC) на объектном хранилище (S3), управляются через **Iceberg** (метаданные, снимки) и доступны через **Trino** (SQL).

### Роль Apache Iceberg

Iceberg переписывает правила управления таблицами в больших озерах данных. В отличие от таблиц в стиле Hive, которые основаны на иерархиях каталогов и статических метаданных, Iceberg обеспечивает высоко оптимизированный слой метаданных, который поддерживает корректную работу с огромными наборами данных.

Это дает:

- ACID-транзакции, целостность данных на объектном хранилище
- Поддерживается эволюция схемы, добавление/удаление колонок происходит без перезаписи данных
- Поддерживаются запросы к историческим снимкам (snapshots)
- Сами снимки (snapshots) обеспечивают воспроизводимость (что может быть важно для регулятора)
- Скрыто выполняется партиционирование для оптимизации запросов
- Возможны row-level security и column-level masking, применяемые во время запроса

### Роль Trino

Trino это распределённый SQL-движок. Он не хранит данные. Его задача — принять SQL-запрос, построить план выполнения, распределить обработку между вычислительными узлами и вернуть результат потребителю. Trino отделяет вычисления от хранения. При росте аналитической нагрузки можно увеличивать вычислительные ресурсы кластера, не перенося сами данные в отдельную СУБД.

Это дает:

- Привычный SQL-доступ в диалекте ANSI SQL
- Можно выполнять запросы к разным источникам: Iceberg, PostgreSQL, Kafka. Т.е. работа строится поверх разных хранилищ
- Массивно-параллельная обработка (MPP)
- Отделение compute от storage, что позволяет довольно гибко масштабироваться

### Плюсы Lakehouse для FinUnion + RetailBank

- Очень высокая масштабируемость, петабайты данных за счет использования S3
- Дешёвое хранение данных, т.к. S3 обходится для хранения дешевле, чем DWH
- Хорошо подходит для плохоструктурированных (JSON, логи, события) данныхсобытия |
- Поддерживается streaming, например из Kafka в Lakehouse
- Возможность работать с сырыми данные для ML (например, для антифрод)
- Высокая гибкость к данным (schema-on-read)
- Очень хорошая воспроизводимость за счет снимков (Iceberg)

### Минусы Lakehouse для FinUnion + RetailBank

- Достаточно высокая сложность, т.к. нужна экспертиза (Iceberg, Trino, S3)
- В общем случае нет ACID, но можно получить ACID-гарантии при реализации через Iceberg
- В общем случае нет привычного SQL-доступа, но можно получить SQL-доступ к данным при реализации через Trino
- Высокая стоимость, нужно будет посчитать, сколько потребуется для S3 + Trino + Iceberg
- Есть задержка, т.к. доступ через Trino медленнее прямого PostgreSQL для маленьких запросов

### Когда Lakehouse подходит

- Когда большие объёмы (петабайты)
- Когда плохоструктурированные (JSON, логи, события) данные
- Когда нужен ML (напрмиер, для антифрод)
- Когда нужен streaming (real-time данные)
- Когда важна гибкость гибкость (schema-on-read)

## Что остается в DWH, что в Lakehouse

В целевой архитектуре будет применяться и DWH и Lakehouse, поэтому нужно определить, как мы будем разделять данные между ними.

### В DWH (PostgreSQL / Greenplum)

- **Агрегации** по клиентам, счетам, транзакциям и т.д. Данные структурированные, хорошо ложится на BI
- **Витрины** для BI. Т.к. есть SQL-доступ и быстрые запросы
- **Регламентированная отчётность**. Это необходимо для регулятора
- **Справочники** (валюты, регионы и т.д.). Т.к. это небольшие объёмы, часто запрашиваемые (маленькие часты запросы)

### В Lakehouse (S3 + Iceberg + Trino)

- **История транзакций и событий** (CDC). Т.к. это в перспективе могут быть петабайты данных и требуется воспроизводимость (снимки)
- **События карточных операций** (streaming). Т.к. это real-time данные, что требуется для антифрода
- **Сырые данные для ML**. Потребуется для антифрода и скоринга рисков по моделям
- **Архивы** (выгрузки, документы). Т.к. имеется дешёвое хранение (S3)
- **Логи**. Это плохоструктурированная информация

## Ограничения

### Ограничения DWH

- Не масштабируется для очень больших объемов (петабайты). Поэтому для больших объемов используем Lakehouse
- Нет streaming. Поэтому для задач, где нужен real-time используем Lakehouse + Kafka
- Нет ML. Для задач ML тоже используем Lakehouse

### Ограничения Lakehouse

- Сложность (Iceberg, Trino, S3). Нужно плавное расширение, возможно длительное во времени. Домен за доменом, а не big-bang. В процессе придет и экспертиза.
- Много маленьких файлов. Нужно планировать compaction (Airflow)
- Стоимость (Iceberg, Trino, S3). Необходимо просчитать расходы, начать с малого объёма
- Есть задержка, особенно для маленьких маленьких запросов, т.к. это не прямой SQL доступ к БД. Поэтому используем DWH для маленьких запросов, а в Lakehouse работаем с большими данными
