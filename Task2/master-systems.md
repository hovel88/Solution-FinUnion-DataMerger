### Два мастера на промежуточном этапе (3 месяца)

Примечание касается таблицы выше. Относительно мастер-систем на промежуточном этапе (помечено звездочкой). Чтобы упросить описание в таблице, мастер системой показана система из FinUnion, но тут надо пояснить, что это только для новых сущностей и прежних сущностей из FinUnion. Это не касается прежних сущностей из RetailBank. Объясню идею на примере Клиента.

!!! . Примечание для ревьювера: я на самом деле не знаю как правильно делать в таких случаях, и возможно я выбрал самый плохой сценарий из возможных. Хотелось бы узнать у Вас, жизнеспособно ли такое, или такое решение принесет только боль и страдания. От такого решения сейчас выстроена вся последующая разработка заданий.

После слияния FinUnion и RetailBank нельзя мгновенно отключить системы RetailBank, потому что:

- Клиенты RetailBank продолжают пользоваться своими продуктами (карты, счета, кредиты), иначе, если сразу отрезать RetailBank, то у клиентов RetailBank будет негативный опыт и посыпятся жалобы, возникнут репутационные риски
- Продукты RetailBank ещё не перенесены в FinUnion
- Сотрудники RetailBank продолжают обслуживать своих клиентов
- Регуляторная отчётность RetailBank должна продолжаться без разрывов

Поэтому важно организовать сосуществование с сопоставлением данных.

На промежуточном этапе (3 месяца) используется модель двух мастеров:

- прежние Клиенты FinUnion — **FU CRM** — полный мастер для клиентов FinUnion
- новые Клиенты (после слияния) — **FU CRM** — все новые клиенты создаются только в FU CRM
- прежние Клиенты RetailBank — **RB CRM** — временный мастер для клиентов RetailBank (пока идёт миграция)
- сопоставляет клиентов FU и RB (identity resolution) — **Integration Layer**
- объединение данных для единой отчетности — **DWH**

После окончательного слияния через 12 месяцев будет один мастер — **MDM Customer Hub** — а RetailBank будет выведен из эксплуатации.

Аналогичная ситуация с двумя мастерами и для других сущностей, для них мастер-системы **FU/RB Core**, **FU/RB Cards**, **FU/RB Loan** разделяются по тому же принципу: прежние сущности из RetailBank читаются из систем в RetailBank, а новые и существующие сущности из FinUnion читаются из систем в FinUnion.

Однако сопоставление в **Integration Layer** проще производить на уровне Клиента, потому что есть общие аттрибуты (ИНН, паспорт, телефон, СНИЛС), а вот со Счетами, Картами, Кредитами и т.д. всё сложнее. Поэтому такие сущности (Счета, Карты, и т.д.) — привязываются уже к сопоставленному клиенту и последующее объединение для отчетов происходит в **DWH**.

При этом, на промежуточном этапе (3 месяца) используется стратегия "главная мастер-система в первую очередь", т.е.:

- новые Клиенты — **FU CRM** (единственный мастер)
- старые клиенты RetailBank — сопоставляются через **Integration Layer (party_id)**
- новые продукты для старых клиентов RB — **создаются в FU** (FU Loans, FU Cards, FU Core) и **связываются с сопоставленным party_id**
- старые продукты клиентов RB — **остаются в RB** (RB Loans, RB Cards, RB Core), пока не мигрируют

Клиент RetailBank после слияния сопоставляется с клиентом FinUnion через Integration Layer (по ИНН, паспорту, телефону). Ему присваивается **единый party_id**. При этом, у клиента получается смешанный портфель по продуктам:

- старый Кредит клиента RB — в **RB Loans** (пока)
- новый Кредит клиента RB — в **FU Loans**
- старая Карта клиента RB — в **RB Cards** (пока)
- новая Карта клиента RB — в **FU Cards**
- старый Счёт клиента RB — в **RB Core** (пока)
- новый Счёт клиента RB — в **FU Core**

Получается, что **Integration Layer** сопоставляет и показывает единую картину (старые + новые) сущности. Он становится ОЧЕНЬ важным связующим элементов в процессе слияния.

## Детализация мастер-систем по сущностям

### 1. Клиент (Party)

| Параметр | Значение |
| -- | -- |
| **Источники As-Is** | FU CRM, RB CRM |
| **Системы-создатели** | FU CRM (для клиентов FinUnion и новых клиентов), RB CRM (для старых клиентов RetailBank) |
| **Мастер на 3 месяца** | **FU CRM** + **RB CRM** (временная) + **правила сопоставления** (identity resolution) |
| **Целевая мастер** | **Customer Hub** — MDM |
| **Связь с BIAN** | Party Reference Data Directory |
| **Обоснование** | Для слияния критично получить единый клиентский идентификатор. Но на 3 месяца два мастера сосуществуют — FU CRM как "ведущая" (мы RetailBank сливаем в FinUnion, все новые клиенты заводятся в FinUnion) и RB CRM (для прежних клиентов RetailBank, чтобы они могли пользоваться услугами), сопоставляемые через Integration Layer с правилами сопоставления, а объединяем это всё в DWH. Через 12 месяцев мастер-системой станет Customer Hub (золотая запись) |
