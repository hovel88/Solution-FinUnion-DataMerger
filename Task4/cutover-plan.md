## 1. Цель переключения

Цель переключения — **перевести клиентские данные** с **двух мастеров** (FU CRM и RB CRM) на **единый MDM Customer Hub**. После переключения система должна **предоставлять единый party_id** для всех клиентов, а данные должны **быть сопоставлены** (identity resolution). Старый контур (FU CRM / RB CRM) сохраняется как **fallback** до завершения периода наблюдения.

## 2. Объём переключения

### 2.1. Включаем

- Все клиенты RB переносим в MDM Customer Hub
- Все клиенты FU переносим в MDM Customer Hub
- Маршрутизация чтения клиентов: FU CRM / Core / Cards / Loans —> API Gateway —> MDM Customer Hub
- Сопоставление (identity resolution) — единый party_id

### 2.2. Не включаем

- Продукты, справочники (этап 5)
- Счета, карты, кредиты (этап 6)
- Транзакции (этап 7)

### 2.3. Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
| -- | -: | -- | -- |
| Все клиенты RB сопоставлены | 100% имеют party_id | MDM UI / SQL | Data Office |
| Все клиенты FU в MDM | 100% имеют party_id | MDM UI / SQL | Data Office |
| Дубли устранены | 0 дублей party_id | SQL (UNIQUE constraint) | MDM Team |
| Чтение из MDM работает | 0 ошибок в API Gateway | Мониторинг | SRE |
| Покрытие тестами | >95% клиентов | Автотесты | Data Team |

## 5. Состояние данных до переключения

| Данные | Источник истины до | Источник истины после | Подготовка | Проверка консистентности | При расхождении |
| -- | -- | -- | -- | -- | -- |
| Клиенты FU | FU CRM | MDM Customer Hub | Выгрузка из FU CRM | Сверка (количество, ИНН) | Откат на FU CRM |
| Клиенты RB | RB CRM | MDM Customer Hub | Выгрузка из RB CRM | Сверка (количество, ИНН) | Откат на RB CRM |
| Сопоставление (party_id) | Integration Layer | MDM Customer Hub | Выгрузка из Integration Layer | Сверка (уникальность) | Исправление дедупликации |

**Контрольные суммы**:
| Проверка | Формула | Целевое значение |
|---|---|---|
| Количество клиентов | `COUNT(*)` | FU + RB = MDM |
| Уникальность party_id | `COUNT(DISTINCT party_id)` | = `COUNT(*)` |
| Контрольная сумма ИНН | `SUM(LENGTH(inn))` | FU + RB = MDM |

## 10. Rollback-сценарий

### 10.1. Условия запуска rollback

| Триггер rollback | Порог | Кто принимает решение | Максимальное время реакции |
| -- | -: | -- | -- |
| Покрытие party_id | < 95% | Head of Order Management | 15 минут |
| Ошибки чтения/записи | > 1% | SRE | 15 минут |
| Дубли | > 0 | MDM Team | 30 минут |
| Сверка не прошла | — | Data Team | 30 минут |

### 10.2. Шаги rollback

| Шаг | Действие | Ответственный | Проверка результата | Что делать с данными, созданными в новом контуре |
| -: | -- | -- | -- | -- |
| 1 | Остановить новые записи в MDM | MDM Team | Запись запрещена | — |
| 2 | Вернуть маршрутизацию на FU CRM / RB CRM | Integration Team | Чтение работает | — |
| 3 | Разрешить запись в FU CRM / RB CRM | SRE | Запись работает | — |
| 4 | Сверить данные (что успело попасть в MDM) | Data Team | Расхождения зафиксированы | Ручная сверка |
| 5 | Уведомить поддержку и бизнес | Head of Order Management | Все уведомлены | — |

### 10.3. Состояние после rollback

| Область | Ожидаемое состояние после отката | Как проверяем |
| -- | -- | -- |
| Трафик | FU CRM / RB CRM принимают | Мониторинг |
| Данные | Нет потерь | Сверка |
| Дубли | 0 | SQL |
| Статусы | Объяснимы | Поддержка |
| Поддержка | Инструкции | Проверка |

**Важно**: фолбэк **возможен** только **до** вывода RB из эксплуатации (этап 8). **После** вывода RB — **только** прямое исправление в MDM.
